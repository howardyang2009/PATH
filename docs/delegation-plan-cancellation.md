# PATH Delegation Plan — Phase 4: Run Cancellation (issues #52–#57)

A delegation plan in the [AI Fluency](https://anthropic.skilljar.com/ai-fluency-framework-foundations) sense: deciding which work is done by the human, which by AI, and in what interaction mode. Scoped to the six tickets that give PATH its first control verb — stopping a run in flight from the CLI, the API, and the viewer.

Predecessor: [Phase 3: MVP Viewer](./delegation-plan-viewer.md), which covered the foundational batch (#41–#45). Phase 3 promised a Phase 4 for the viewer UI-surface build; those surfaces (#46–#49) and the two bugs the dogfood pass found (#50, #51) shipped as v0.3.0 and v0.3.1 **without a separate plan document** — the arrangement Phase 3 described was simply carried forward unchanged. This document is the first re-decision since, and it is a re-decision because the work has changed character: every phase so far has been read-only. This one writes.

## Problem awareness

The destination is an operator being able to **stop a run and trust what the system then says about it**. Today interrupting `path run` kills the process mid-step and leaves the run's row saying `running` forever; the viewer can watch a runaway LLM fan-out but not stop it. Six tickets close that gap: external abort in the engine (#52), graceful `^C` (#53), a cancel route (#54), a client method (#55), a viewer button (#56), and a live acceptance pass (#57).

**The close that IS "done" is [#57](https://github.com/howardyang2009/PATH/issues/57)** — a real release-notes pipeline cancelled mid-fan-out through the viewer, and the same pipeline `^C`-ed under the CLI, with the run record, the log stream, and the on-disk context all agreeing afterwards. Nothing before #57 is evidence that cancellation works; it is only evidence that it compiles.

The main failure mode of this phase is **claiming a cancel that never happened**. This is the [#51](https://github.com/howardyang2009/PATH/issues/51) lesson generalized: a surface must not assert what it cannot know. Cancellation offers three fresh chances to break that rule — a route that 202s for a run it holds no controller for, a button that says "Cancelling…" when the request was refused, a row that says `cancelled` while a child process is still alive. Every one of them passes a green test suite.

The second failure mode is **scope creep into retry and resume**. Both are explicitly deferred (mvp spec §1, §10). This phase makes a stop *truthful*; it does not make it *resumable*, and a ticket that starts reasoning about restarting from a checkpoint has left its lane.

Work order from the blocking graph: **#52 is the entire frontier** — it is the only unblocked ticket, and the other five wait on it. Then #53 and #54 open in parallel, #55 follows #54, #56 follows #55, and #57 needs both #53 and #56. The dependency chain is deeper than Phase 3's and there is no parallelism until #52 lands, so #52's quality sets the ceiling for everything else.

## Platform awareness

- **What makes this delegable:** the decisions are already made and written down. [#52](https://github.com/howardyang2009/PATH/issues/52) carries a decision table settled in a grilling session — the cancel unit, the terminal status, the event shape, the route and its four responses, the error policy, the button's friction — and the other five tickets refer back to it rather than re-deciding. `CONTEXT.md`, `mvp-spec.md` §5.6, and `server-api-spec.md` §6 are the fixed points each item verifies against, and §6 has been holding a door open for the cancel route since it was written.
- **Where AI is strong here:** threading an existing `AbortSignal` seam outward (#52); a route in an established regex-matched handler style with an existing vitest pattern (#54); a typed client method beside three siblings (#55); a React affordance against pinned tokens (#56).
- **Where the risk concentrates:**
  - **Long-lived interfaces, two of them.** `RunOptions.signal` (#52) is the engine's public entry point for every future consumer, and `cancelRun()` (#55) is the first write verb on the `@path/client-core` seam that the designer and any mobile surface import. Phase 2's #15 and Phase 3's #41 both taught the same thing: cheap to shape now, expensive forever after.
  - **Silent failure surfaces, three of them.** The backwards-compatibility default on `run-cancelled.cause` (#52) — get it wrong and every pre-existing NDJSON log stops replaying, which surfaces as a viewer that mysteriously fails to open old runs, not as a failing test. The abort/publish race (#52) — a cancelled step must land no publishes, and "no publishes landed" is exactly the kind of assertion that passes because the timing happened to be favourable, the #24 concurrency lesson. The controller registry (#54) — an entry that outlives its run leaks, and an entry missing when the run is genuinely live means a refused cancel.
  - **What AI cannot verify unattended:** the button's *feel* (#56) — whether the armed state reads as armed, whether ~3s is long enough to notice and short enough not to annoy, whether it is distinguishable without relying on hue. And the whole of #57, which needs a hand on the mouse and a real SDK turn unwinding.
- **External risk:** real, and structurally stuck at the back. #57 is the only item that spends money on live Agent SDK calls, and it is the *last* item in the chain — the opposite of pulling external risk forward. Mitigation, since the graph cannot be reordered: #52 and #54 both carry end-to-end coverage through the scripted-worker seam (`RunOptions.llmWorker`), so wiring surprises surface without spend, and the human should `curl` the route by hand the day #54 lands rather than first meeting it in #57.

## Task delegation

In frontier order. "Automation" = AI implements and verifies, human reads the `/code-review` output and diff summary. "+ focused review" = plus one named thing the human personally inspects. "+ adversarial review" = the human attacks a silent failure mode rather than reading for it. "Augmentation" = human in the loop, because AI cannot self-verify what is being judged.

| Issue | Who leads | Mode | Human discernment focus |
|---|---|---|---|
| [#52 engine external abort](https://github.com/howardyang2009/PATH/issues/52) | AI | Automation + focused review + **adversarial** | Three foci, because this ticket carries every kind of risk at once. **Focused:** the shape of `RunOptions.signal` — the public way in, permanent once consumed. **Adversarial ×2:** replay a *real* pre-existing v0.3 dogfood NDJSON log (`docs/dogfood/.path/`) through `readNdjsonLog` yourself and confirm the `cause` default holds; then attack the abort/publish race — cancel repeatedly at different moments in a multi-step run and confirm no publish from a cancelled step ever reaches `context.json` |
| [#53 CLI graceful SIGINT](https://github.com/howardyang2009/PATH/issues/53) | AI | Automation + focused review | The **escape hatch and the cleanup**: a second `^C` really exits during a slow unwind, the listener is removed once the run settles, and `main` still never calls `process.exit` on the graceful path (`cli.ts:322`). The real key-press lives in #57 |
| [#54 server cancel route](https://github.com/howardyang2009/PATH/issues/54) | AI | Automation + **adversarial review** | **Attack the honesty of the 202.** Cancel a CLI-launched run through the route; cancel a `running` row left behind by a killed server; cancel the same run twice; cancel one that finished a millisecond ago. Each must answer truthfully (404 / 409 / 409 / 202) and never promise a stop it cannot perform. Then confirm the registry is empty after every outcome, including the rejected-promise path, and that the new route is not swallowed by the SPA fallback |
| [#55 client-core `cancelRun()`](https://github.com/howardyang2009/PATH/issues/55) | AI | Automation + focused review | The **seam's first write verb** — method shape, `void` return, and the error contract (`PathApiError.status` preserved so a caller can tell 404 from 409). Every future client inherits this; ratify it before #56 builds on it |
| [#56 viewer Cancel button](https://github.com/howardyang2009/PATH/issues/56) | **AI + human in the loop** | Augmentation | Human reacts to the interaction: does the **armed state read as armed** without relying on colour, is the **~3s disarm** right, does the button vanish cleanly when a terminal status folds in from the stream. Plus one thing the human checks personally: that the pane **never claims a cancel it did not get** — a refused 409 must show its message, not "Cancelling…" |
| [#57 acceptance: live cancel](https://github.com/howardyang2009/PATH/issues/57) | **Human** | Augmentation | The yardstick. The human starts the pipeline, watches the fan-out, clicks Cancel, `^C`s the CLI run, and personally checks the row, the events, the context, the replay of both old and new logs, and the exit code. AI assists with the assertions; it does not declare the pass |

### Rationale

- **#52 gets three foci, which is unusual and deliberate.** Phase 3 gave #41 two because it mixed a long-lived interface with a silent failure surface. #52 mixes a long-lived interface with *two* silent failure surfaces of different kinds — a compatibility default whose breakage is invisible until someone opens an old run, and a race whose breakage is invisible until it corrupts a publish. These are three separate jobs: read the shape, replay an old log, attack the timing. Uniform diff-reading would catch none of them.
- **#54 is adversarial-only, with no focused-review item.** There is no long-lived interface here — the route's shape was settled in the grilling and written into the ticket, so there is nothing left to ratify. What remains is entirely about honesty under conditions AI will not think to construct: a run in another process, a stale row, a double click, a race with terminality. Those are attacks, not readings.
- **#56 is augmentation where Phase 3 would have said automation.** The React work itself is mechanical, but two of its three requirements — the arm timing and legibility without hue — are pixel judgments, the same category as #44's layout. The difference from #44 is that here the human's reaction is a *correction* to a working thing rather than the deliverable itself, so the mode is augmentation without a prototype detour.
- **#57 is the only human-led item, and it must stay that way.** This is the discernment trap the framework names and the reason #26 and the viewer dogfood pass were both human-led: AI may not both implement cancellation and certify that cancellation works. It also carries the phase's only real spend, which is a second reason a human decides when it runs.
- **The board is otherwise automation-heavy, consistent with Phases 2 and 3** — and for the same structural reason. The grilling session spent human judgment up front on the eleven decisions in #52's table precisely so the build would not need it per-ticket. An implementer who disagrees with a locked decision opens that conversation on the ticket; it does not appear as a silent diff.

## Cross-cutting practices (Description + Diligence)

- **Process description is standardized:** #52–#56 each run as a fresh-context `/implement` session against the issue — TDD slices, then two-axis `/code-review` (Standards + Spec), then a commit referencing the issue. Context is cleared between tickets; the ticket plus #52's decision table is the contract, never conversation memory. #57 is not an `/implement` session at all — it is a human at a terminal and a browser.
- **Performance description:** commits reference issue numbers; each closing comment states what was verified and how — which vitest cases, and for #52 and #54 explicitly which adversarial checks were performed and what they showed. A closed blocker must actually mean *done*, or the five tickets downstream of #52 inherit the lie.
- **Creation diligence:** the eleven decisions in #52's table are fixed for this phase — a change is a conversation on the ticket, not a diff. **Retry and resume stay out** (mvp spec §1); anything discovered mid-ticket that wants them goes to the tracker as a new issue. No existing NDJSON log may become unreadable and no existing log-event member may gain a required field (the additive rule stated in `logging/log-event.ts`). No new dependency and no version bump is needed by any of these six tickets; a diff that contains one has drifted.
- **Transparency diligence:** #52–#56 are AI-implemented with human review concentrated exactly as the table above describes; #57 is human-performed. This document is the record of that arrangement, and `CHANGELOG.md` records the acceptance pass including whatever turned out to be wrong.
- **Deployment diligence — the non-delegable sign-offs, by name:**
  1. **#52's `RunOptions.signal` shape** — approved by the human before #53 and #54 build on it.
  2. **#52's compatibility replay** — the human personally replays a pre-existing v0.3 NDJSON log. Not a test AI wrote and ran; the actual old file.
  3. **#55's `cancelRun()` contract** — approved before #56 consumes it, as #41's public API was in Phase 3.
  4. **#57, the acceptance close** — the human clicks Cancel, presses `^C`, and signs off. This is the feature's release decision and may not be delegated.

## Trigger for the next plan

When #57 closes, cancellation is done and the natural next effort is the one this phase deliberately refused: **retry and resume**. That is not a six-ticket feature with its decisions already settled — it is fog (is a resume a new root run or a continuation, what makes an already-written blob reusable, how does a `while-do` resume mid-iteration), so it wants a wayfinder map before it wants a delegation plan. Re-decide the split in a **Phase 5** plan once that map's investigation tickets have produced decisions. Expect it to tilt *back* toward augmentation: unlike this phase, its hard parts are semantic rather than mechanical.
