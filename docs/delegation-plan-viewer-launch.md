# PATH Delegation Plan — Phase 4: Viewer Discover & Launch (map #228)

A delegation plan in the [AI Fluency](https://anthropic.skilljar.com/ai-fluency-framework-foundations) sense: deciding which work is done by the human, which by AI, and in what interaction mode. This is the build-phase plan for the [discover-and-launch viewer map (#228)](https://github.com/howardyang2009/PATH/issues/228) — turning the read-only viewer into one that lists every `*.workflow.json` under the project and launches one from the browser, streaming the new run live.

Predecessor: [Phase 3: MVP Viewer](./delegation-plan-viewer.md), which shipped the read-only viewer (#41–#45) — the run list, the indented run tree, the SSE narrative, the masked blob panes, and the `@path/client-core` read seam every surface here reuses. That phase's guardrail was *read-only*; this phase deliberately crosses it, on the narrow, pre-litigated path the map fixed. This plan re-tilts toward automation for the same reason Phase 3 did: the map's decisions and the amended [server-api-v0.md](./api/server-api-v0.md) / [server-api-spec.md](./spec/server-api-spec.md) are fixed points every ticket verifies against.

## Problem awareness

The destination is map #228's reached-criterion: against a real project root, the viewer **discovers** all root `workflow.json` files, **launches** one with operator-supplied raw-JSON `input`/`config`, and streams the accepted run live — the same live tree + SSE narrative Phase 3 already renders, now reached from a launch instead of a pre-existing run. **The close that IS "done" is the dogfood/acceptance sign-off** — the human opens the browser, launches the release-notes workflow, and watches it stream to `succeeded`.

Three surfaces carry the phase, and two of them already landed while the decisions were being closed:

- **Discovery endpoint** — `GET /v0/workflows` in `@path/server` ([#243](https://github.com/howardyang2009/PATH/issues/243)). Spec'd ([server-api-v0.md §6](./api/server-api-v0.md), [#230](https://github.com/howardyang2009/PATH/issues/230) → [#236](https://github.com/howardyang2009/PATH/issues/236)), **not yet built**. This is the frontier: the one surface still fog, and the one that unblocks the other two end-to-end.
- **client-core write surface** — `startRun(options)` + `listWorkflows()`. **Built and merged** ([#232](https://github.com/howardyang2009/PATH/issues/232) → [#239](https://github.com/howardyang2009/PATH/issues/239)); `packages/client-core/src/api-client.ts`.
- **Viewer launch UI** — the inline launch panel, raw-JSON input/config with validation and the post-`202` transition into the live run. **Built and merged** ([#233](https://github.com/howardyang2009/PATH/issues/233), commit `b8d8406`); `packages/viewer/src/launch-panel.tsx`, wired in `app.tsx`.

The consequence of that build order is the plan's central fact: **the client and the UI are already calling `listWorkflows()` against an endpoint the server does not answer.** Until the discovery route ships, the launch panel has nothing to list — the phase is one server addition away from being demonstrable, and every other ticket here is verification, wiring, or a flagged follow-up, not net-new frontier.

The main failure mode of this phase is **the security fork going quiet**. The map re-opened a boundary it had earlier held closed: operator override config now **rejects `$env`** ([ADR 0012](./adr/0012-operator-config-rejects-env-wrapper.md), [#231](https://github.com/howardyang2009/PATH/issues/231)) because the browser launch surface hands a would-be env-read power to a caller who cannot author a `binary` step. That reject is enforced in `POST /v0/runs`, not in the new endpoint — but this phase is the reason it exists, so it is this phase's adversarial target.

## Platform awareness

- **What makes this delegable:** the contract is fully written before any code — [server-api-v0.md §6](./api/server-api-v0.md) fixes the response shape, the scan rules, and the root-classification algorithm; [valid-root-detection.md](./research/valid-root-detection.md) proves the classification sound; the loader primitives (`loadWorkflowTree`, `tree.files` as the transitive nested-ref set) already exist. The endpoint is written *to* a spec, not inventing one — exactly the shape Phase 3's server tickets had.
- **Where AI is strong here:** the discovery route is a mechanical, well-specified `@path/server` addition against an existing vitest style (mirror `list-runs.ts` / `post-runs.ts`): a directory walk, a per-file `loadWorkflowTree`, an absolute-path set-subtraction, a snake_case response. Deterministic, table-testable, no judgment call left open.
- **Where the risk concentrates:**
  - **Silent-wrong classification:** the `is_root` flag is a set-subtraction over canonicalized paths. The known traps are all named in the research doc — a lexical `resolve` (not `realpath`) so a symlink cannot alias a nested file as a root, a load *failure* yielding `is_root: null` (not `false`) because a failed `LoadResult` carries no `tree.files`, and a file that is both a root and someone's nested ref. Each passes a naive green test and mislabels a real workflow.
  - **The scan boundary:** the walk must skip `.path/`, `node_modules`, and dot-dirs, and must **not** follow symlinks. A miss here surfaces `.path/`-internal or dependency workflow files as launchable, or escapes the project root.
  - **The security fork (adversarial):** `$env` rejection ([ADR 0012](./adr/0012-operator-config-rejects-env-wrapper.md)) lives on `POST /v0/runs`, reached now from a browser. The composed `{"$secret": {"$env": "NAME"}}` form must be rejected as hard as the bare wrapper, and an `$env` authored *inside* a `workflow.json` must be **untouched**. This is a `400` that a green happy-path test never exercises.
  - **What AI cannot verify AFK:** the launch panel's feel — does the raw-JSON textarea's validation read clearly, does the post-`202` hand-off into the live run feel continuous, is the invalid-workflow row legible. Already built (#233), but the *dogfood* judgment on it is human.
- **External risk:** now non-trivial for the first time in the viewer line. This phase makes the browser a **run-triggering** surface, and CSRF/cross-origin was deliberately split out of the config envelope ([#237](https://github.com/howardyang2009/PATH/issues/237), still open) rather than solved here. The plan treats #237 as a **named gate on the dogfood close**, not an optional follow-up: a same-origin no-auth endpoint that starts runs is the exact shape that gate guards.

### Rationale

- **The board is automation-heavy by design**, mirroring Phase 3: the map spent the human's judgment on the irreversible calls (list-all-flag-roots over roots-only, the `$env` reject, raw-JSON over a schema-form, the camelCase-in/wire-out seam) precisely so the build would not need it per-ticket. The locked decisions win; an implementer disagreement is a map-amendment conversation, not a silent diff.
- **The discovery endpoint is the only real frontier**, and it is single-focus: it has one non-obvious way to be silently wrong — mislabelling `is_root` — and the research doc already enumerates every trap. Name that one thing; reading the rest of the diff line-by-line catches nothing.
- **Two surfaces are already built** (#239, #233), so their rows are ratification, not construction. They stay in the plan because the phase is not *done* until they run end-to-end against the live endpoint, and because the client-core seam is a *long-lived interface* (designer + mobile import it) whose shape the human still signs off, exactly as Phase 3 did for #41.
- **The security fork gets adversarial review on its own line** even though the code lives on the pre-existing `POST /v0/runs`. This phase is why the reject exists — the browser is the caller that breaks the old "`$env` adds no new power" equivalence — so the human attacks it here: the composed-wrapper bypass and the authored-`$env` false-positive are the two ways it goes quietly wrong.
- **The yardstick stays human.** The dogfood close is this phase's #26 (Phase 2) / the Phase 3 acceptance close: AI must not both build the launch path and declare its own acceptance passed. It is **human-led / Augmentation**, and it is gated on [#237](https://github.com/howardyang2009/PATH/issues/237) — a run-triggering browser surface does not sign off while its CSRF/origin gate is still open.

## Cross-cutting practices (Description + Diligence)

- **Process description is standardized:** each server/type ticket runs as a fresh-context `/implement` session against the issue — TDD slices, then two-axis `/code-review` (Standards + Spec), then commit referencing the issue. Context is cleared between tickets; the ticket + map decisions + the ADRs are the contract, never conversation memory.
- **Performance description:** commits reference issue numbers; each closing comment states what was verified and how (which vitest cases, which adversarial checks — specifically, for the discovery endpoint, which of the [valid-root-detection.md](./research/valid-root-detection.md) traps has a test).
- **Creation diligence — the scope line for this phase is sharper than Phase 3's,** because this phase deliberately crossed the *read-only* guardrail. What is in: discovery, the write seam, the raw-JSON launch panel. What stays out and goes to the tracker, not the diff: the schema-derived launch form (operator chose raw JSON — deferred), authoring/editing workflows in the viewer (designer territory), and any per-key config denylist (parity with CLI `--set` — [ADR 0012](./adr/0012-operator-config-rejects-env-wrapper.md) ruled it out). `is_root` is a presentation hint, **not** a launchability gate ([ADR 0011](./adr/0011-discovery-lists-all-workflows-roots-flagged.md)) — the endpoint must not start refusing to list, or refusing to launch, an inner workflow.
- **Transparency diligence:** the discovery endpoint, the type consolidation, and the already-merged client-core/launch surfaces are AI-implemented with human review concentrated as the table describes; this document is the record of that arrangement, including the two surfaces that landed ahead of it.
- **Deployment diligence — the non-delegable sign-offs, by name:**
  1. **The `@path/client-core` write surface** (#239) — the public `startRun`/`listWorkflows` shape, approved by the human as a long-lived interface the designer and mobile import ([ADR 0013](./adr/0013-client-write-seam-camelcase-in-wire-out.md)).
  2. **The `$env` reject** — the human personally confirms the adversarial cases (composed wrapper rejected, authored `$env` untouched) before the launch surface is called done. A security boundary is not "passed" by a green happy-path suite.
  3. **The dogfood / acceptance close** — the human launches a real workflow from the browser and watches it stream to terminal, and **[#237](https://github.com/howardyang2009/PATH/issues/237) (CSRF/origin gate) is resolved or explicitly waived** before this sign-off. This is the phase's release decision and may not be delegated.

## Trigger for the next plan

When the discovery endpoint ships and the three surfaces run end-to-end — the dogfood close signed off and [#237](https://github.com/howardyang2009/PATH/issues/237) resolved — the viewer's discover-and-launch loop is complete. The next map is not a viewer phase: it is the **designer** (authoring/editing workflows in the browser), which the read-only and now launch-only scoping has deferred at every turn, or the **mobile** surface that imports the same `@path/client-core` write seam this phase ratified. Re-decide the split when that destination is charted.
