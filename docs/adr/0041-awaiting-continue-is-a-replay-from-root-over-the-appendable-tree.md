# Awaiting Complete continues by replaying from the root over the appendable tree

A `person-activity` step parks its run at `awaiting` and the engine tears down (ADR 0039). Completion is a fresh engine invocation with its **own entry point**, distinct from launch and from Resume: `POST /v0/runs/:step_run_id/complete` acquires a single-writer lease on the root run, replays the tree **from the root** reusing every `succeeded` node's output and restoring every re-entered workflow-run's context (the same `planReuse` + restore-by-load primitives Resume uses), reaches the parked leaf as the one non-terminal node, writes the person's output as that leaf's output blob, transitions the leaf `awaiting → succeeded`, and continues the walk forward. Unlike Resume it does **not** mint a successor root: every write lands in the **existing** tree. This is the *appendable-tree exception* to the rule that a run's rows are read-only — and its scope is narrow.

## Considered options

**Continue targeted at the leaf, not from the root.** The tempting shape is "restore the awaiting step's context, continue from there" — touch only the parked leaf's enclosing run. We rejected it. Continuation in a nested tree is not forward-from-the-leaf; it is a **stack unwind up to the root**: after the leaf finishes, control returns to its sequence, then to the enclosing workflow-run, then to a `collect` join, then to the root tail. Every frame on that path carries its own context blob, its own inherited config, its own remaining-sibling cursor, and — inside a `while-do` — its own iteration scope (ADR 0037). Rebuilding every ancestor frame from the store *is* the root walk, so targeted-open does not avoid the walk; it re-implements it by hand and re-hits the loop-cursor ambiguity #420 already ruled on (plan-reuse cannot locate the next step in a loop without a per-iteration cursor). Replay-from-root gets the whole reconstruction for free by reusing the walk Resume already ships: off-path `succeeded` runs are reused read-only, the awaiting-path runs are re-entered live.

**One shared entry point with debug-stepping.** #461 and #465 framed the mechanism as "Model Q, shared with debug-stepping #419." That sharing never happened: map #419 committed no spec and no ADR, `paused` is not a status, and debug-stepping is deferred indefinitely (research `docs/research/issue-462-debug-stepping-and-model-q.md`). There is no second consumer to parameterize for, so person-activity owns this mechanism outright. This ADR replaces the "shared with debug" language in ADR 0039 and CONTEXT.md; "Model Q" is dropped as a name (it lived only in closed issue bodies).

**A leaf CAS as the only guard.** Multiple `awaiting` leaves may complete in parallel, and each Complete replays from the root. A per-leaf compare-and-swap (`awaiting → succeeded`) alone stops a double-submit on the *same* leaf but not the cross-leaf race: two invocations completing two sibling branches both reach the `collect` join, both see both branches `succeeded`, both pass the join, and both run the shared tail — double execution with real side effects. So the guard is **tree-level**: a per-root-run **expiring store lease** (the ADR 0017 lease pattern) lets one Complete advance a tree at a time; a concurrent Complete is rejected `409` and the person retries (never queued — a queue re-introduces the held wait ADR 0039 removes). An invocation that reaches a *still-awaiting* sibling parks at the incomplete join and releases; whichever Complete last satisfies the join runs the tail, exactly once. The leaf CAS remains as the write precondition (a Complete on a non-`awaiting` leaf is rejected `409`).

## Consequences

- **The exception is narrow.** The only writes that break read-only-ness are the parked leaf's status transition (`awaiting → succeeded`) and its output blob. Successor row appends, the monotonic `seq`, and `context.json` write-through are ordinary behavior of a still-`running` run resumed — the enclosing workflow-run was never terminal (ADR 0038), so nothing was frozen (ADR 0032 freezes only a terminal predecessor when a successor starts). No new persistence exception is needed for context.
- **Idempotency is free; crash-atomicity is not promised.** Because the continue is replay-with-reuse, any re-invocation reuses every `succeeded` row and re-drives only the unfinished tail; the stored leaf output means no re-submission. But a crash *between* the leaf commit and the tail's end strands a `running` tree with no awaiting leaf to re-trigger it — the same failure mode as a crash mid-launch, which PATH does not auto-heal today. ADR 0039's durability promise is scoped to "a parked await survives restart and can still be Completed," not "continuation is crash-atomic." A general running-tree recovery sweep is a future cross-cutting item, not person-activity's.
- **Allowed transition chains.** Leaf: `awaiting → succeeded` (valid output), `awaiting → awaiting` (invalid output refused `400`, ADR 0040), `awaiting → cancelled` (Cancel; #461: Complete always succeeds, failure is Cancel) — never `awaiting → failed`. Tree, once a Complete drives it forward: `running → succeeded` (tail all succeeds), `running → failed` (a successor step or checkpoint fails), `running → running` with a new `awaiting` leaf (a later person-activity step, or park-at-join on a still-awaiting sibling), `running → cancelled` (operator cancel). The appendable window opens at the first `awaiting` and closes the instant the tree reaches a terminal status; a Complete on a terminal tree, or on a non-`awaiting` leaf, is rejected.
- **The route is thin.** `POST /complete` responds `202` after validating and committing the leaf, and drives the tail in the background; a long tail must not hold the HTTP request.
- **Complete reloads the workflow file**, the same requirement Resume carries (ADR 0039): a moved file or relocated store must still resolve for the replay to run.
- The current in-memory `CompletionRegistry` + `live.complete` path (research finding C, commit 81ad9c9) is superseded by this design and is not the engine contract.
