# PATH Delegation Plan — Phase 5: API-Endpoint Door Evidence (issues #130–#135)

A delegation plan in the [AI Fluency](https://anthropic.skilljar.com/ai-fluency-framework-foundations) sense: deciding which work is done by the human, which by AI, and in what interaction mode. Scoped to the six tickets of [wayfinder map #129](https://github.com/howardyang2009/PATH/issues/129) — the map that fires the API-endpoint door's trigger honestly and earns a verdict on it.

Predecessor: [Phase 4: Run Cancellation](./delegation-plan-cancellation.md), which covered #52–#57. Phase 4 promised a Phase 5 once the next door had a wayfinder map behind it, and predicted the split would **tilt back toward augmentation** because the hard parts would be semantic rather than mechanical. Both halves held, with one correction: the door that came next was not retry/resume. The [v-next register (#109)](https://github.com/howardyang2009/PATH/issues/109) orders the doors, and it put `$env` first (shipped v0.4.3 via map [#113](https://github.com/howardyang2009/PATH/issues/113), which ran without a plan document because Phase 2's build arrangement carried forward unchanged) and the API-endpoint door second. This document is the re-decision, and it is a re-decision because the work has changed character again: every phase so far produced a **system**. This one produces a **judgement**, and the thing that gets built is deliberately not the deliverable.

## Problem awareness

The destination is **an evidence-backed verdict on the API-endpoint door**: what `curl`-through-`binary` actually costs in a real HTTP pipeline, and therefore whether the door opens with a follow-on map named, or gets re-parked in #109 with a sharper trigger. The map is explicit that "curl is fine" is a **permitted and equal outcome**.

**The close that IS "done" is [#135](https://github.com/howardyang2009/PATH/issues/135)** — the `API-endpoint step type` entry in #109 carrying an outcome, with reasoning that points at recorded observations from a real run rather than at intuition, and mvp-spec §10's row updated if the verdict changes what it should say. Nothing before #135 is a verdict; #133 closing means only that a workflow ran.

The main failure mode of this phase is **a motivated verdict** — concluding "build the step type" because the map exists, six tickets were spent, and building is more satisfying than re-parking. This is the framework's discernment trap in an unusually pure form. Every phase so far could check its own work against a spec; this one is being asked to decide whether a spec change is warranted, and the same agent that fights `curl` quoting for an afternoon is the one that reports how much the quoting hurt. The map's countermeasure is structural — the rubric is pre-registered in #130 and recording is a separate ticket (#134) from building (#133) — and this plan's job is to make sure the delegation does not quietly dissolve that structure by putting one agent, in one context, across all three.

The second failure mode is **scope creep into the design**. #129 rules the step type's format shape, schema ownership, engine reader, and failure typing out of scope, along with retry/backoff and rewiring `release-notes.workflow.json`. A ticket that starts sketching a `"type": "api"` node has left its lane and has also pre-empted the verdict.

The third is **the credential**. This phase is the first to run a real secret against a live third-party API. `$env` masking covers persisted artifacts; it does not cover the process table, and the token-in-argv exposure is itself a rubric entry (mvp-spec.md:374). The failure mode is not the finding — the finding is the point — it is the token reaching a committed file, an issue comment, or a pushed run artifact.

Work order from the blocking graph, as the ticket bodies record it (GitHub has no native blocking relation; the convention is `Blocked by: #N`, same as maps #1, #29, #40, #113):

```
#130 rubric ─────────────────┐
                             ├──→ #134 record ──→ #135 verdict
#131 shape ──┐               │
             ├─→ #133 build ─┘
#132 token ──┘
```

The frontier is **three-wide** — #130, #131, #132 are all unblocked and unclaimed, the widest opening any phase has had. Phase 4's frontier was a single ticket whose quality set the ceiling for five others; here three sessions can run in parallel on day one.

**One edge the graph does not carry, and this plan makes binding:** #133 is blocked by #131 and #132 only, but the map's locked decision says the rubric is fixed **before a line of workflow JSON exists**. If #133 runs first, #130 is written by someone who already felt the pain, and pre-registration becomes theatre. The graph will not stop that — the tracker's blocking is on #134, which is too late. **#130 must close before #133 starts.** Treated here as a diligence rule rather than a new edge, because it constrains *starting*, which blocking cannot express.

## Platform awareness

- **What makes this delegable:** the judgements are front-loaded into ticket bodies and the map's Notes, and #129 carries a block of **locked decisions from pre-chart grilling** that no ticket may re-litigate — the verdict is the destination not the step type, the rubric is pre-registered, the workflow is real not a probe, it lives in `docs/dogfood/` and runs live, spec §11 acceptance is untouched. The fixed points each item verifies against exist and are normative: [CONTEXT.md](../CONTEXT.md) (invariant 3, one output object per step), [workflow-format-v0.md](./format/workflow-format-v0.md) (§4.2 non-zero exit fails the step, §8.3 the `$env`/`$secret` wrapper), [mvp-spec.md](./spec/mvp-spec.md) (§10's door row, and :374 on argv exposure), and `docs/dogfood/changelog.workflow.json` as the shape the new workflow follows.
- **Where AI is strong here:** writing a format-v0 workflow against an existing sibling file and iterating it until it runs (#133) — this is mechanical, well-specified, and has a fast feedback loop; mapping a commit range onto GitHub REST or GraphQL endpoints and reporting what each returns (#131's research half, #132's verification call); and transcribing observations against a fixed standard (#134).
- **Where the risk concentrates:**
  - **The yardstick, twice.** #130 *is* the yardstick and #135 *applies* it. An AI that writes the rubric can write one its own later work will clear, and an AI that weighs the evidence can weigh it toward the more interesting outcome. Neither is a diff a human can read after the fact; both are judgements that have to be made with a human in the room.
  - **Silent failure surfaces, two of them.** First, **a rubric entry that is unobservable as written** — #134 must notice a hole in the standard rather than silently scoring it a pass, and a pass and an unobservable both look like "no pain recorded". Second, **the clean entries** — an entry where `curl` was simply fine is the finding that keeps the door shut, and #134's body flags it as the one a motivated reader skips. Under-reporting the clean entries is exactly how a motivated verdict gets built out of honest-looking parts.
  - **What AI cannot verify unattended:** whether the pain it felt was *real cost* or *unfamiliarity*. An agent that has never authored a v0 workflow by hand cannot distinguish "this quoting is genuinely unreasonable" from "I got it wrong twice". That distinction is the whole evidentiary content of the map, and it needs the human who will live with the format.
  - **The credential surface.** Token in argv is a *finding to record*; token in a commit is an incident. `$env` masking is v0.4.3-new and #133 explicitly names a masking surprise as itself a finding — which means the first real exercise of the wrapper must be inspected by a human, not certified by the agent that triggered it.
- **External risk is at the front for the first time.** #132 is real auth against a live third-party API, and it sits on the opening frontier rather than at the back of the chain — the inverse of Phase 4, where #57's live SDK spend was structurally stuck last and had to be mitigated with scripted-worker coverage. Take the win: run #132 early even if the human's attention that week is on #130 and #131, because an unexpected scope or rate-limit answer changes #131's endpoint choice. Cost risk is negligible (GitHub's API is free; the authenticated limit is 5000/hr against 60/hr unauthenticated), so the front-loading costs nothing.

## Task delegation

In frontier order. "Automation" = AI performs, human reviews output. "+ focused review" = plus one named thing the human personally inspects. "+ adversarial review" = the human attacks a silent failure mode rather than reading for it. "Augmentation" = human and AI collaborate, human in the loop, because AI cannot self-verify what is being judged. "Agency" = AI works independently inside guardrails the human set in advance.

Note that no ticket in this phase carries `ready-for-agent`. That is accurate rather than an oversight: four of the six are HITL by their wayfinder type.

| Issue | Who leads | Mode | Human discernment focus |
|---|---|---|---|
| [#130 pre-register the rubric](https://github.com/howardyang2009/PATH/issues/130) | **Human** | Augmentation (`/grilling`) | The yardstick, written before the work it measures. The human decides **what counts as pain versus annoyance** on each entry, cuts the entries that are theatre (author readability is the map's own weakest candidate), and settles the **weighing rule** — whether the argv entry promotes the door on its own or the verdict needs a threshold across several. AI drafts testable phrasings and argues the entries; it does not choose the bar |
| [#131 pipeline shape](https://github.com/howardyang2009/PATH/issues/131) | **AI + human in the loop** | Augmentation (`/grilling`) | Two calls the human owns because they change what the evidence *is*: **REST versus GraphQL** (a query body to quote is a different quoting experiment than a `?q=` search string), and **how the token reaches `curl`** — `-H` into argv versus `--config -` on stdin versus `.netrc`. Whether a usable alternative to argv **exists** is itself evidence about the door, so it must not be settled by whichever form the agent typed first. AI leads the endpoint survey and the node list |
| [#132 GITHUB_TOKEN provisioning](https://github.com/howardyang2009/PATH/issues/132) | **Human** (acquisition) / AI (verification) | Augmentation | Split at the secret boundary. The **human obtains the token and places it in the environment**; the agent never handles, prints, or echoes its value. AI then verifies end-to-end — one authenticated call per endpoint #131 will use, rate-limit headers back as expected — and records **only** the variable name, source, scopes, and limit. The human's focus: confirm the recorded artifact contains no value, and that the chosen source (`gh auth token` versus a fine-grained PAT) is written down well enough that the run reproduces |
| [#133 build and run it live](https://github.com/howardyang2009/PATH/issues/133) | AI | **Agency** | The guardrails are the deliverable's integrity, and they are already written into the ticket: no engine change, no schema change, `release-notes.workflow.json` untouched, no retry or backoff, and **keep the wreckage** — every failed attempt, quoting fix, and confusing error stays reachable, because it is the evidence. The human sets those guardrails and stays out of the loop; intervening to *help* the agent past a quoting problem destroys the measurement. One human check on completion: the `.path/` run directory and the workflow JSON contain no raw token |
| [#134 record against the rubric](https://github.com/howardyang2009/PATH/issues/134) | AI, **except entry Q6** | Automation + **adversarial review** | **One observation is human-performed:** [rubric](./research/api-door-rubric.md) entry **Q6 (locatability)** is a claim about a *reader*, so it is observed by a human who did not write the workflow — not the #133 agent, not an agent carrying its context. Then **attack the under-reporting.** Read the clean entries first, not the painful ones — an entry that says `curl` was fine is what keeps the door shut, and it is the one a motivated write-up thins out. Then check each entry marked unobservable is genuinely a hole in the standard and not a pass in disguise, and that anything unanticipated is labelled as such rather than folded in as if pre-registered. The human is checking for a thumb on the scale, not for prose quality |
| [#135 the verdict](https://github.com/howardyang2009/PATH/issues/135) | **Human** | Augmentation (`/grilling`) | The yardstick applied. The human weighs #134's observations against #130's rubric under the rule #130 fixed, and picks one of the three outcomes — door opens, re-parked with a sharper trigger, or the frame was wrong. AI assembles the evidence and argues each outcome; it does not declare the verdict, and it does not draft the #109 edit before the human has said which way it goes |

### Rationale

- **#130 and #135 are the two human-led tickets, and they are the same job split in time.** One writes the bar, the other measures against it. Phase 4 had exactly one human-led item (#57, the acceptance close) for the same reason the framework names: AI may not both build a thing and certify it. This phase inherits that rule twice over, because the "thing" being certified is a claim about how much AI-authored work hurt.
- **#131 is augmentation, not automation, despite looking like a research ticket.** The endpoint survey is genuinely delegable. But two of its decisions **choose the experiment**, not the implementation: REST versus GraphQL determines what the quoting evidence even looks like, and the argv-versus-stdin choice determines whether the phase's most serious rubric entry gets exercised at all. An agent optimizing for a working pipeline would reasonably reach for whichever form it knows best — and would, without meaning to, quietly settle the door.
- **#133 is the phase's only agency item, and the guardrail list is why.** It is the one ticket where the human should *not* be in the loop: help offered mid-fight contaminates the measurement, and a human who steps in to fix a quoting problem has converted evidence into a smooth experience. Agency is safe here precisely because the boundaries are unusually crisp and were fixed before the work — no engine change, no schema change, no retry, one named file. The instruction "if something feels missing in v0, that feeling is the deliverable — record it, do not fix it" is what makes an otherwise-tempting scope creep a violation rather than initiative.
- **#134 is adversarial-only, with no focused-review item.** There is no long-lived interface here and nothing to ratify; the standard was fixed in #130. What remains is entirely about honesty under a condition AI will not think to construct against itself — that the write-up is produced downstream of an afternoon of frustration. Reading it for accuracy will not catch a thumb on the scale; reading it clean-entries-first will.
- **#133 and #134 must be separate agent sessions with fresh context.** The map made them separate tickets; delegation makes them separate contexts. An agent carrying #133's transcript into #134 is reporting its own experience from inside the frustration, and the pre-registration structure the map spent a whole ticket on buys nothing.
- **The board is augmentation-heavy, inverting Phases 2–4.** Those phases were automation-heavy because a grilling session had spent the human judgement up front and the tickets that followed were construction. Here construction is a *single* ticket (#133) and the other five are judgement — deciding what to measure, how to measure it, and what the measurement means. This is the tilt Phase 4 predicted, arriving one door earlier than it expected.

## Cross-cutting practices (Description + Diligence)

- **Process description is standardized, per type.** #130, #131 and #135 run as `/grilling` + `/domain-modeling` sessions, one question at a time, with the human answering for themselves — an agent that answers its own grilling questions has broken the HITL contract and produced nothing. #132's verification half and #133 run as fresh-context agent sessions against the issue body, with the map's Notes as the contract; conversation memory is never the contract. #134 runs in a fresh context that does **not** inherit #133's. Every ticket is claimed by assignment before work starts, so concurrent sessions on the three-wide frontier do not collide.
- **Performance description:** each ticket closes with a resolution comment stating what was decided or observed and against what — for #132, the variable name, source, scopes and verified rate limit (and no value); for #133, the command run, the range used, and where the wreckage lives; for #134, the filled rubric as a linked asset. The map's **Decisions so far** gets a one-line pointer per close, by ticket name. A closed ticket must mean the question is actually answered, or #135 weighs a lie.
- **Creation diligence:** #129's locked decisions are fixed for this phase — a change is a conversation on the map, not a diff. **No engine change, no schema change, no format change** ships from any of these six tickets; the API-endpoint step type is not designed here, retry and backoff are #109's third door, and `release-notes.workflow.json` is not rewired. New files land only under `docs/dogfood/`. No dependency and no version bump is needed by any ticket in this phase; a diff containing one has drifted. Spec §11's acceptance set stays offline and dependency-free.
- **Secret diligence, specific to this phase:** the token's value never enters a workflow file, a `--config` file, an issue comment, a linked asset, a commit, or an agent transcript. It is referenced only as `{"$secret": {"$env": "GITHUB_TOKEN"}}`. Its appearance in argv is a **finding to record**, not an incident — and the distinction between the two is exactly why the human, not the agent, checks the artifacts before anything is pushed.
- **Transparency diligence:** #131's survey, #132's verification, #133 and #134 are AI-performed with human review concentrated as the table describes; #130, #132's acquisition half and #135 are human-performed. This document is the record of that arrangement. If the verdict opens the door, #109's entry should say the evidence came from an AI-built pipeline judged by a human, because that is a caveat a future reader of the rubric is entitled to.
- **Deployment diligence — the non-delegable sign-offs, by name:**
  1. **#130's rubric and its weighing rule** — approved by the human, and **frozen before #133 starts**. Not merely before #134, which is when the tracker's blocking would enforce it. Settled and landed as [`docs/research/api-door-rubric.md`](./research/api-door-rubric.md); the freeze is git-verifiable, since the rubric's commit must predate the workflow's first.
  2. **#131's token-transport choice** — the human ratifies whether the run exercises argv exposure or an alternative, because that choice determines whether the phase's most serious entry is tested at all.
  3. **#133's artifacts, before anything is committed or pushed** — the human personally greps the `.path/` run directory, the produced notes, and the workflow JSON for the raw token. Not a check the agent ran and reported; the actual files.
  4. **#135, the verdict** — the human weighs and decides, and personally edits #109's row. This is the phase's release decision and may not be delegated. If the evidence does not clear the bar #130 set, the door stays shut, and that is a successful phase.

## Trigger for the next plan

Which plan comes next is decided *by* #135, and the three outcomes fork cleanly:

- **Door opens** → the follow-on is a fresh wayfinder map whose destination is the step type's *design* (format shape, schema ownership, engine reader, failure typing) — explicitly out of scope here. A **Phase 6** build plan follows that map's decisions, and should look like Phases 2–4: automation-heavy, because the judgement will already have been spent. Expect one long-lived interface to ratify (the node's format shape, permanent under strict unknown-field rejection) and one silent failure surface (a typed non-2xx that must not lie about which failure it was).
- **Re-parked with a sharper trigger** → no plan is due. #109's next door is **retry/resume**, which the register puts last and which *redraws the destination* rather than extending it (§1 rules it out of scope, §5.6 is fail-fast). It wants a wayfinder map before it wants a delegation plan, and that map's own tickets will be judgement-shaped again.
- **The frame was wrong** → whatever #135 names — a `path`-native HTTP client, or a `binary`-worker concern like scoped env — is a new effort with a new destination, and gets its own map first. Re-decide the split once that map has produced decisions.

In all three cases the next document is written after a map exists, not before. That ordering is now the repo's pattern rather than a preference: #113 shipped a door without a plan document because Phase 2's arrangement fit unchanged, and this phase needed a plan precisely because the arrangement did not.
