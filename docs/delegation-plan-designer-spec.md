# PATH Delegation Plan — Phase 6: Designer Spec (map #254, issues #255–#263)

A delegation plan in the [AI Fluency](https://anthropic.skilljar.com/ai-fluency-framework-foundations) sense: deciding which work is done by the human, which by AI, and in what interaction mode. Scoped to the eight tickets of [wayfinder map #254](https://github.com/howardyang2009/PATH/issues/254) — the map that specifies **`@path/designer`**, the surface where a workflow is *authored*.

Predecessor: [Viewer Discover & Launch](./delegation-plan-viewer-launch.md) (map #228). Its closing trigger named this map by name — "the next map is not a viewer phase: it is the **designer**" — and both of the gates it set have since closed: [#237](https://github.com/howardyang2009/PATH/issues/237) (CSRF/origin gate) and [#244](https://github.com/howardyang2009/PATH/issues/244) (dogfood acceptance). The origin gate closing is what lets map #254 lock decision 8 by reuse rather than re-deciding it.

*On numbering:* the predecessor's title reads "Phase 4" while [API-Endpoint Door Evidence](./delegation-plan-api-door.md) also claims Phase 5; the labels collided. This plan takes **Phase 6** as the next unused number rather than renumbering history. The lineage that matters is the link above, not the integer.

This is the first plan since [Phase 1: MVP Spec](./delegation-plan.md) whose deliverable is **documents**, and the split re-tilts accordingly: Phase 4's board was automation-heavy because a written contract already existed to verify against. Here the phase's whole job *is* writing that contract, so the board tilts hard back to augmentation.

## Problem awareness

The destination is map #254's reached-criterion: **`docs/spec/designer-spec.md` exists and is normative enough that a build map can be charted from it without re-opening any decision, and every ADR it depends on is merged.** No Designer gets built this phase — construction is a separate execution map that this spec seeds.

**The close that IS "done" is [#263](https://github.com/howardyang2009/PATH/issues/263).** Every other ticket closing means a decision was *made*; only #263 means it was *written down normatively*, with the write route landed in [server-api-v0.md](./api/server-api-v0.md), the ADRs merged, and `Designer` in [CONTEXT.md](../CONTEXT.md)'s glossary. A board of eight green tickets with no assembled spec is a phase that produced conversation.

The main failure mode of this phase is **prose that reads normative and is not**. A spec section can name a decision, sound settled, and still leave the actual choice implicit — and this is precisely the failure AI-drafted spec text produces most fluently. The destination criterion is stated as a negative ("without re-opening any decision"), which no green check can confirm; it is a judgement, and the phase's structural countermeasure is that the *decisions* close on separate tickets, in separate sessions, before the assembly ticket writes anything. The delegation must not dissolve that by letting #263 quietly re-decide something #256–#261 left vague.

The second failure mode is **re-litigating the locked list**. Map #254 carries fourteen locked decisions from pre-chart grilling, including one deliberate reversal of closed map [#40](https://github.com/howardyang2009/PATH/issues/40). A grilling session is *designed* to reopen questions; pointed at decisions 1–14 it burns the phase. Every ticket respects them; a genuine disagreement is a map-amendment conversation on #254, not a spec line that quietly contradicts it.

The third failure mode is **[#256](https://github.com/howardyang2009/PATH/issues/256) getting the id-stability call wrong**, and it deserves separate naming because its failure is silent, delayed, and externally visible. A canvas editor rewrites the whole file on save. If a re-save re-mints node GUIDs, nothing fails: the file validates, the workflow runs, tests stay green. The damage surfaces later, when someone resumes a prior run and watches already-succeeded steps re-execute — and resume is at-least-once, so re-execution can re-fire external effects. That is the one decision on this map whose wrongness cannot be caught by looking at the spec.

### Work order

**The blocking edges below are inferred, not recorded.** Unlike maps [#1](https://github.com/howardyang2009/PATH/issues/1), [#29](https://github.com/howardyang2009/PATH/issues/29), [#40](https://github.com/howardyang2009/PATH/issues/40) and [#113](https://github.com/howardyang2009/PATH/issues/113), none of #255–#263 carries a `Blocked by:` line — every sub-ticket says only `Part of #254`. First housekeeping action of this phase: add the edges to the issues so the tracker, not this document, is the authority.

```
#262 canvas library (AFK) ──┐
                            ├──→ #255 interaction model ──→ #261 v1 palette ──┐
                            │                                                 │
#256 node identity ──→ #257 write route ──→ #258 edit lease ──────────────────┼──→ #263 assemble
                                                                              │
#259 serving mounts ──────────────────────────────────────────────────────────┤
#260 run surfaces + client-core seam ─────────────────────────────────────────┘
```

The frontier is **four-wide** — #262, #256, #259, #260 are all unblocked — the widest opening any PATH phase has had. Two dependencies are worth stating because they are not obvious:

- **#262 before #255.** The library survey answers whether nested containers and undrawable-invalid-edges are *available*; prototyping an interaction model that no candidate library can express, and hand-rolling is unwilling to carry, wastes the prototype. #262 is also the only ticket with real wall-clock latency (an AFK subagent), so firing it first costs nothing.
- **#256 before #257.** The write route's contract depends on who mints ids: server-stamped ids change the request shape and add a response body the client must reconcile; client-minted ids leave the route a pure byte-writer. Deciding the route first would prejudge the identity question by accident.

## Platform awareness

**What makes this batch delegable.** Unusually much, for a spec phase. The map arrives with fourteen decisions already locked, so no ticket faces an open field. [CONTEXT.md](../CONTEXT.md) is canonical for the vocabulary — node types, joins, identity, config inheritance. [server-api-v0.md](./api/server-api-v0.md) is both the fixed point #257 extends *and* the shape #263 imitates, including its `## 0. Constraints (from the map, not re-litigated here)` convention, which gives the locked decisions a pre-agreed landing place. And every decision points at code that already exists: `resolveWorkflowPath` ([post-runs.ts:26](../packages/server/src/routes/post-runs.ts#L26)), the symlink stance in [get-workflows.ts](../packages/server/src/routes/get-workflows.ts), `enforceSameOrigin`, the SSE hub in [run-event-hub.ts](../packages/server/src/run-event-hub.ts), and the exported seam in [client-core/src/index.ts](../packages/client-core/src/index.ts). These tickets specify *against* a system, not into a vacuum.

**Where AI is strong here.** Enumeration and drafting. #257's status-code matrix, path-encoding options and edge cases; #258's lease state machine and its failure table; #262's capability sweep across React Flow and alternatives; #263's prose against an existing template. Also raw prototype velocity — #255 wants a concrete artifact to react to, and the fastest route to one is AI-built, following the [launch-panel.prototype.html](../packages/viewer/src/launch-panel.prototype.html) precedent from map #40.

**Where the risk concentrates.**

- **Long-lived interfaces.** The #257 write route enters [server-api-v0.md](./api/server-api-v0.md) permanently and every future client codes to it. The #260 client-core additions are the *third* surface on a seam whose stated rule is that surfaces must not reach different answers. Both outlive this phase by more than anything else on the board.
- **Silent failure modes.** #256 (id re-mint, described above) and #258 (lease correctness: clock skew, the evicted-but-alive session, markers surviving a server restart). Both are decidable on paper and both fail invisibly if decided wrong — the lease's dominant failure is not a crash but a file that stays locked, or a lock that yields while its holder is still typing.
- **Taste.** #255 (does depth-3 nesting read, does the reorder gesture feel right) and the presentation half of #261 (inherited-vs-overridden config). AI cannot judge these at all, and confident AI prose about them is worse than silence.
- **What AI cannot verify unattended.** #262's answers are the sharpest case: library documentation states intent, not behaviour, and the licence-tier question is contractual. A survey that reports "nested sub-flows: first-class" from a marketing page, or misreads what the free tier permits for this use, is a wrong foundation the whole build sits on.

**External risk, pulled to the front.** #262 is the only ticket that depends on the outside world — third-party capability and third-party licensing, neither of which the project controls — and it is scheduled first for exactly that reason. If React Flow's free tier does not permit this use, or no library does controlled state over nested containers, the hand-rolled baseline becomes the answer and #255 and #261 must be prototyped against it. Discovering that after the interaction model is pinned is the expensive order.

### Rationale

- **The board is augmentation-heavy, inverting Phase 4's**, and the reason is structural rather than a change of confidence in AI. Phase 4 could delegate because a written contract already existed to verify each ticket against. Six of these eight tickets *are* the writing of that contract; there is nothing to check them against except judgement. Expect the successor plan — the build map this spec seeds — to swing back to automation, exactly as Phase 1 → Phase 2 did.
- **#262 gets full agency where nothing else does.** It is bounded (seven questions), verifiable after the fact (its claims are checkable against primary sources), reversible (a throwaway branch), and slow in wall-clock terms — the textbook agency profile. The human's role is not to supervise the search but to spot-check the two claims the build would be built on.
- **#259 is the only automation row** because it is the only ticket whose answer is largely determined by existing code: one static dir today, a documented default, a known no-op-on-missing behaviour, and a locked decision fixing the topology. The interesting part is a constraint to preserve, not a design to invent — so name the constraint and skip the line-by-line.
- **#255 is human-led even though AI does most of the typing.** The prototype is an artifact for a human to react to; the reaction is the deliverable. Delegating the reaction would produce an interaction model validated by the thing that drew it.
- **#258 is attacked, not reviewed.** A lease protocol reads correct in every draft — the failures live in interleavings and in wall-clock time, which prose does not surface. The human's job on this ticket is to construct the four hostile timelines named above and make the spec answer each one.
- **#256 and #261 are the same risk in two shapes**: an authoring tool that silently damages a file it was trusted to edit. They are the two rows where "the spec looks fine" is the least reassuring possible evidence, and they are both human-led for that reason.
- **The yardstick stays human at #263.** This is the phase's version of Phase 2's #26 and Phase 4's dogfood close. The framework's discernment trap here is unusually sharp: the same model that drafts the spec is the natural candidate to assess whether the spec is complete, and it will assess fluently. The destination confirmation is a human sign-off, listed below.

## Cross-cutting practices (Description + Diligence)

**Process description, standardized per ticket type** — the map's working notes fix the skills, and this plan fixes the session shape around them:

- Decision tickets (#256, #257, #258, #259, #260, #261): a fresh-context session running `/grilling` + `/domain-modeling` against the issue body. The contract is the issue + map #254's locked decisions + the named ADRs — never conversation memory, and never a sibling ticket's session transcript.
- #255: `/prototype`, artifact linked as an asset on the issue, following the [launch-panel.prototype.html](../packages/viewer/src/launch-panel.prototype.html) precedent.
- #262: `/research` subagent, throwaway branch, fired explicitly by the driving dev — the map states subagents are not auto-fired here.
- #263: a fresh-context assembly session reading the *closed issues*, not the sessions that closed them.

**Performance description — where the record lives.** Map #254's `## Decisions so far` section is currently empty and is this phase's running ledger: each ticket's close appends the decision there, in one or two lines, before the issue is closed. Each closing comment states **what was decided and what it forecloses** — a decision ticket that closes with "discussed, see thread" has produced nothing #263 can assemble from. The map's `## Not yet specified` list is the other half of the ledger: seven items are parked there, and the ones that graduate this phase (canvas validation UX after #255; undo/redo and dirty state after #255 + #258) move out of it explicitly rather than by silence.

**Creation diligence — the scope line.** No production code lands this phase. The only code written is the #255 prototype and the #262 research branch, both throwaway, neither merged to `main`. Out and to the tracker rather than into a spec section: `path/workflow@2` DAG format (decision 6, its own map if ever), a shared `@path/ui` React package (decisions 5 and 14), building the Designer (the execution map), mobile surfaces, and auth/remote/multi-project. And the standing rule for this map: **decisions 1–14 are not re-litigated.** A ticket that concludes against one of them stops and amends #254 in the open, which is a legitimate and cheap outcome; a ticket that quietly writes a contradicting spec line is not.

Two traps specific to a documents phase are worth pinning:

- **Do not spec what a ticket did not decide.** If #260 does not settle whether the Designer needs a run browser, #263 writes it into `## Not yet specified`, not into a section that reads like a decision.
- **ADRs are earned, not enumerated.** #263 lists five candidates; the three-part bar is the filter, and writing five ADRs because five were listed is the failure mode.

**Transparency diligence.** The spec, the ADR drafts, the prototype and the survey are AI-drafted or AI-produced with human-owned decisions, in the modes the table records. Each ADR names the decision as human-made where it was — the reasoning is the artifact, and its provenance is part of it. This document is the record of the arrangement.

**Deployment diligence — the non-delegable sign-offs, by name:**

1. **The node-identity round-trip guarantee** (#256) — the human approves the minting authority and the named test that would catch a re-mint. Nothing downstream can detect this being wrong.
2. **The write route wire contract** (#257) — the human approves verb, path encoding, precondition and status codes before they enter [server-api-v0.md](./api/server-api-v0.md), which is permanent and multi-client.
3. **The `@path/client-core` additions** (#260) — the human approves what moves down into the shared seam, as Phase 4 did for [ADR 0013](./adr/0013-client-write-seam-camelcase-in-wire-out.md). Third surface, same seam, same signature required.
4. **The unrenderable-node stance** (#261) — the human approves whether the Designer opens an arbitrary existing workflow, and what a save does to what it could not render.
5. **The destination confirmation** (#263) — the human, reading the assembled spec cold, judges that a build map can be charted without re-opening a decision, and approves the `Designer` entry in [CONTEXT.md](../CONTEXT.md). This is the phase's release decision and may not be delegated.

## Trigger for the next plan

When #263 closes — spec merged, ADRs merged, `Designer` in the glossary — map #254 is reached and the **execution map** for building `@path/designer` is charted as a fresh effort. Re-decide the split then, and expect it to invert this one: a locked spec plus a fixed wire contract is exactly the fixed point that made Phase 2 and Phase 4 automation-heavy, and the build tickets will have one for the first time. The rows to watch in that re-decision are the ones this phase could only decide on paper — the lease's real behaviour under crash and sleep, and whether the id-stability guarantee survives contact with the canvas library's state model.
