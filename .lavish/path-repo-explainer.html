01 The core equation

Everything in PATH's vocabulary hangs off one decomposition. CONTEXT.md is canonical — code, specs, and issues use these terms exactly.

Step
what to do. One input object, one output object. Never says who runs it.
+
Worker
who / where it executes — local engine, LLM subagent. Inherited downward unless overridden.
=
Task
A step bound to a worker.
→
Run
One executing instance of that task, on a Processor (a live worker instance).
Invariant 2 is the one that surprises people. There is no separate "workflow execution" concept. A workflow is itself a valid step type — workflow-as-step — so executing a workflow means running the task of the step that wraps it. The top-level workflow gets an implicit root step, and a workflow-step's run spawns child runs, forming the run tree.

Node grammar — what can sit in a workflow body

Step has a run

The only node type that executes on a worker. Everything else is engine-evaluated.

Parallel logicer

Join modes: collect (MVP), wait-one and do-not-wait deferred.

Branch logicer

Routes. Picks an arm by condition — does not assert.

While-do logicer

Mandatory max-iterations bound; exceeding it fails the run.

Checkpoint engine-evaluated

Fail-fast assertion. True continues, false stops the run as failed. Never exercises judgment.

The judge-step pattern

Any check that needs judgment (human or LLM) becomes a normal step that outputs a verdict, followed by a checkpoint that tests it. branch routes; checkpoint asserts.

Blocks nest arbitrarily (the nested block grammar); checkpoints may appear anywhere in a sequence. Source: CONTEXT.md, packages/schema/src/nodes.ts.

04 The audit chain — three stages of narrowing

PATH keeps three progressively narrower records of what happened. Knowing which one you are looking at tells you what is guaranteed to be in it.

STAGE 1 — widest

Observation

Every typed record of run activity the engine emits to its observer. The engine's only audit seam.

  • Carries payloads: input, output, context, stderr
  • Three exist for persistence alone and are never narrated: step-stderr, step-usage, context-changed
  • Already secret-masked when it crosses the seam
STAGE 2 — narrated subset

Log event

The append-only subset that reaches a log backend, payloads stripped to blob refs on the run row.

  • Envelope: seq (monotonic per root run — the ordering truth), ts, type, run_id, node_id
  • Covers step lifecycle and control-node activity: branch-taken, checkpoint-passed/-failed, iteration-started, loop-exited, join-applied, run-cancelled
  • Projection is not one-to-one — a workflow-run's start and a leaf step's start are both step-started
STAGE 3 — per-predicate

Trace

The evaluation record carried by condition-bearing log events.

  • The condition tree annotated per leaf
  • Each leaf's dot-path, outcome (true / false / error), and the actual value read
  • Values are post-masking

Backends and secrets

Log backend

A dumb sink implementing open / write / close, instantiated per root run. The engine serializes writes and delivers fully-formed, already-masked events. Fan-out is engine-level config. MVP default: SQLite log table + per-root-run NDJSON, both on. A backend write failure fails the run.

Secret

A config value wrapped as {"$secret": ...}. Secrecy rides the value through shallow-merge inheritance. Every secret is scrubbed from all persisted artifacts — log events, input/output objects, context.json, error strings, stderr, condition trace values — replaced with [secret:<key>]. Workers still receive real values: masking is an audit-surface concern, not a dataflow restriction.

05 Config vs. context — the rule worth memorizing

Two key-value stores that look alike and behave nothing alike.

 ConfigContext
Direction Flows in from outside — author at design time, operator at launch time. Written from inside — produced by steps at runtime.
Typical content API tokens, model names, endpoints, flags. A computed temp dir, a branch name, accumulated results.
Scope Declared per step; inherited from the enclosing workflow when unspecified. One workflow-run, isolated. A nested workflow-step starts with a fresh, empty context.
Crossing a boundary Shallow-merge inheritance downward; secret wrappers ride along. Exchanges data with the parent only through the step's input and output objects.
Can a step create it? No — config never originates from execution. Yes — that is the whole point.

06 The v0 HTTP surface

Small on purpose. POST /v0/runs returns before the run finishes — the client then polls the run row or streams events.

RouteDoesNote
POST /v0/runsStart a runResponds before execution finishes
GET /v0/runsList root runsNo output/usage/tree — fetch the run for that
GET /v0/runs/:root_run_idRun status + treeAuthoritative queryable step record
GET /v0/runs/:root_run_id/blobs/:run_id/:nameOne run's input or output objectWhere stripped payloads live
POST /v0/runs/:root_run_id/cancelStop a root run in flightBest-effort; no deadline, no force path
GET /v0/runs/:root_run_id/eventsSSE event streamReplayable by seq via Last-Event-ID
Cancellation is honest about being best-effort. The engine asks — kills the child process, tears down the processor — and holds no deadline and no force path. Two causes: operator (a cancel request against a root run) and sibling-failed (a parallel branch failed, so in-flight siblings are cancelled). A cancelled run ends cancelled, a distinct status from failed — an operator stopping a run is not the workflow breaking. It lands no publishes and is narrated by a run-cancelled event carrying its cause.

08 Running it

No build step and no linked binaries on your PATH — pnpm exec path-server will not find anything. The bins are TypeScript entry points run through tsx.

Verify the workspace

pnpm install
pnpm -r run typecheck
pnpm -r run test

Run a workflow directly

npx tsx packages/engine/bin/path.ts run <workflow.json>
  [--config <config.json>] [--set key=value]

Serve it and watch

pnpm --filter @path/viewer run build
npx tsx packages/server/bin/path-server.ts . --port 8080

Project-directory gotcha

path-server's first argument is the project directory — where .path/ is read and written, defaulting to cwd. The engine CLI instead derives its project directory from the workflow file's own location. These differ, and issue #59 was exactly this mismatch.

09 Where the project stands

The release history reads as one repeated move: take something the codebase already did at every call site, and do it once in one place.

ReleaseThemeWhat landed
v0.4.0 Cancellation Stopping a run in flight from the CLI (^C), the API (cancel route), and the viewer (Cancel button) — acceptance run included. Issues #52–#57.
v0.4.1 Engine interior seams Gave the engine's interior the seams it lacked.
v0.4.2 Owners for the ownerless Six architecture-review candidates, five built and one refused: RunArchive (reading a run back), LiveRuns (running one over HTTP), encodeEventFrame (framing an event on the wire), runNode (running one node of a body), and eventOutcome/buildRunTree (saying what a run's events mean).
v0.4.2 is source-compatible where it counts. The v0 wire format, every HTTP status, and the CLI surface are unchanged. The break is confined to what workspace packages export to each other: Project.db is now Project.archive, and @path/engine no longer exports getRunsForRoot, listRootRuns, or readJsonBlob.

Known rough edges, accepted deliberately

  • #60 — a forced second ^C leaves a lying running row. Accepted as the price of the escape hatch and documented in mvp spec §5.6; the ^C notice now names the cost and the remedy.
  • Long agent cycles — the "limit hit mid-merge" failure mode can recur. Recovery: check git status for a half-finished merge before rerunning the loop.
