What PATH is

Four ideas carry the whole system. Read these first; everything below is detail.

1. A workflow is a file

One JSON file. It holds steps (do work), logicers (route work), and checkpoints (assert). A workflow is itself a valid step type, so files nest.

2. A run is the only execution

There is no separate "workflow execution" concept. Every execution is a run of a task. A workflow-run spawns child runs. Those runs form a run tree.

3. Config in, context out

Config flows in from outside (author or operator). Context is written from inside (steps at runtime). The line never blurs.

4. Everything is audited

The store .path/ holds run rows and a log narrative in SQLite plus per-run blobs. Secrets are masked at the persistence boundary.

The execution model

One equation and one recursion explain how PATH runs anything. A step says what. A worker says how. Bind them and you get a task. Execute a task and you get a run. Because a workflow is a step type, a run spawns more runs.

What runs the routing?

Steps execute on workers. Logicers and checkpoints do not — the engine evaluates them. They have no worker, no task, no run.

  • parallel races or gathers branches — joins collect / wait-one / do-not-wait
  • branch first true arm wins; no match fails the run
  • while-do a mandatory max-iterations bound; overrun fails
  • sequence holds a node array where a slot needs several nodes
  • checkpoint asserts data; false stops the run as failed

The workflow file

A single strict JSON file, versioned path/workflow@3. Every node carries a durable GUID id and a human name. Below: a step, a worker choice, config, and a $secret wrapper. 

{
  "format": "path/workflow@3",
  "id": "a1b2…-uuid",   // machine identity, never regenerated
  "name": "release-notes",
  "config": { "model": "claude-…",
              "token": { "$secret": { "$env": "GITHUB_TOKEN" } } },
  "body": [
    { "type": "binary",  "name": "collect",
      "command": "git", "args": ["log", "--oneline"] },
    { "type": "prompt",  "name": "draft",
      "worker": "sdk",      // pick a worker by name; else the type's default
      "prompt": "Summarize ${context.collect}" }
  ]
}
binary & prompt are not privileged — they are the first two step-type plugins (folders under step-plugins/).
${config.x} and ${context.y} interpolate in allow-listed positions only.
Validity is registry-relative: a file is valid against the plugins the tree actually holds.

Run, stop, resume

A run can stop from a crash or a cancel. Resume re-runs the stopped tree as a successor — it reuses every node that already succeeded and re-runs the rest.

  • path run <file>
    validate the whole tree, then execute a root run
  • stops
    crash or ^C cancel; rows keep the truth of where it got to
  • --resume <root-run-id>
    a successor run; reuses succeeded nodes as reuse rows
Resume is at-least-once. A re-run step can fire an external effect again (a git push, an API POST). The engine cannot detect or prevent the duplicate — the workflow author must make steps idempotent.

Ubiquitous language

CONTEXT.md is canonical. Code, specs, and issues use these terms exactly. The most load-bearing ones:

Step / Worker / Task

Step = what. Worker = a named run method (the how). Task = the bound pair.

Run / Processor

A run is one executing instance of a task. A processor is one live worker instance it runs on.

Run tree / Run kind

Runs under one root form a tree. Four kinds: root run, nested workflow-run, leaf step, reuse row.

Config vs Context

Config flows in from outside and inherits downward. Context is written from inside, isolated per workflow-run.

Logicer / Checkpoint

Engine-evaluated routing and assertion nodes. No worker, no task, no run.

Join mode

collect waits all, wait-one races, do-not-wait fires and forgets.

Secret / Env-sourced

$secret masks a value; $env sources it. Scrubbed at the persistence boundary.

Observation / Log event

The engine emits typed observations at one masked choke point. Narrated ones become log events.

Viewer vs Designer

The viewer watches runs. The designer authors files. Both ride the same client-core.
